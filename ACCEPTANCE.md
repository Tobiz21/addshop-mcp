# Приёмка Addshop MCP клиентом

Все сценарии сначала запускаются с `apply=false`. Для записи используется только
отдельный неопубликованный товар с названием, начинающимся с `MCP TEST`.

## 1. Диагностика

1. `addshop_contract_health` — ожидается `all_ok=true`.
2. `addshop_audit_store` — сверить количества сущностей с админкой.
3. `addshop_create_snapshot` — сохранить snapshot ID перед тестированием.
4. `addshop_describe_entity_form` — сверить варианты категорий, статусов и справочников.
5. `addshop_search` — найти тестовый объект по названию и точному ID.

## 2. Карточка товара

1. Прочитать товар и сохранить revision.
2. Preview изменения названия, описания и SEO.
3. Применить одно поле, повторно прочитать и вернуть исходное значение.
4. Убедиться, что устаревший revision отклоняется без POST.

## 3. Варианты

1. Прочитать offers.
2. По очереди проверить цену, артикул, остаток, размер, цвет и infinite stock.
3. После каждого изменения вернуть исходное значение.

## 4. Медиа

1. Настроить `ADDSHOP_UPLOAD_ROOT` на отдельную тестовую папку.
2. Preview загрузки JPEG/PNG/WebP.
3. Проверить отказ для файла вне папки, неподдерживаемого формата и файла >10 MiB.
4. Загрузить тестовое изображение и проверить новый image ID.
5. Удаление пока выполняется вручную: MCP намеренно не удаляет без prepare-token.

## 5. Характеристики и связи

Проверить `add_property`, `update_property`, `add_tag`, `add_relation` и
`update_video`. После действия повторно прочитать компоненты. Удаления отключены.

## 6. Создание сущностей

Создать тестовую категорию/страницу/новость сначала через preview. Проверить, что
MCP возвращает ровно один новый ID. Удалить тестовые сущности вручную после приёмки.
Важно: в Addshop сам GET `/add/` уже создает объект. Поэтому preview не обращается
к этому URL, а apply выполняет его ровно один раз и проверяет redirect ID.

## 7. Пакетная работа

1. Создать snapshot.
2. Подготовить изменения двух тестовых объектов.
3. Проверить preview diff.
4. Применить batch и проверить новые revisions.
5. Отдельно смоделировать устаревшую revision: ни одна операция не должна начаться.
6. Проверить, что публикация без `confirm_publish=true` блокируется.

## 7a. Заказы и персональные данные

1. Прочитать order summary без флага — контакты и адрес должны быть redacted.
2. Сверить подписи статуса, оплаты, доставки и источника.
3. Включать `include_personal_data=true` только для конкретной задачи клиента.
4. Проверить, что локальный snapshot также не содержит контакты и адреса.

## 7b. Роли

1. `reader`: все записи должны блокироваться, preview и чтение доступны.
2. `content`: разрешены каталог, контент, варианты, медиа и характеристики.
3. `commerce`: разрешены заказы и справочники продаж, каталог недоступен для записи.
4. `admin`: доступны все реализованные записи, но удаления и bulk import всё равно запрещены.

## 7c. Журнал и пользовательский код

1. Установить `ADDSHOP_ACTOR` и выполнить тестовую запись.
2. Проверить событие через `addshop_audit_log` и `chain_valid=true`.
3. Убедиться, что журнал содержит только имена полей, но не значения и контакты.
4. Проверить HTML с iframe/form/eval — scanner должен вернуть high risk.
5. Сохранение high-risk вставки без `confirm_external_code=true` должно блокироваться.

## 7d. Снимки и аварийная защита

1. Создать snapshot и проверить наличие SHA-256.
2. Изменить тестовый объект и получить его через `addshop_compare_snapshot`.
3. При `ADDSHOP_WRITES_ENABLED=0` любая apply-операция должна блокироваться.
4. Установить лимит 1 запись/минуту и проверить открытие circuit breaker.
5. Поврежденная audit chain должна полностью блокировать последующую запись.

## 7e. Сессия и развёртывание

1. Создать DPAPI-сессию через `session_login_cli.py`.
2. Удалить переменную `ADDSHOP_COOKIE`; MCP должен работать через session file.
3. Проверить, что другой Windows-пользователь не может расшифровать файл.
4. Проверить отказ для файла другого shop origin и просроченной сессии.
5. `addshop_local_doctor` не должен возвращать cookie, пароль или токены.

## 8. SEO

Запустить аудит товаров, категорий и страниц. Проверить пустые SEO-поля, тонкие
описания, дубли title и slug. Исправления сначала передать в batch preview.

## 8a. Массовая работа с товарами

1. Отобрать товары каждой комбинацией selector.
2. Проверить процент основной цены и SEO templates в preview.
3. Изменить одну revision и убедиться, что старый expected map блокирует apply.
4. Отдельно проверить цены вариантов и порог подтверждения 50%.
5. Смоделировать ошибку в середине пачки и проверить обратный rollback.
6. Запустить quality audit и сверить несколько проблем вручную.

## 8b. Создание полного товара

1. Подготовить specification без публикации и получить plan hash.
2. Изменить specification — старый hash должен быть отклонен.
3. Создать тестовый товар с вариантом, характеристикой и изображением.
4. Проверить, что публикация выполняется только последним шагом.
5. Смоделировать ошибку изображения и убедиться, что карточка осталась скрытой.
6. Проверить recovery journal и audit log.

## 8c. Blueprint, сравнение и CSV

1. Получить blueprint товара и убедиться, что publish=false и изображения не скачаны.
2. Сравнить две карточки и вручную проверить несколько различий.
3. Экспортировать CSV, изменить одну карточку и получить preview.
4. Изменить товар после экспорта — импорт старой revision должен блокироваться.
5. Изменить CSV после preview — старый plan hash должен блокироваться.
6. Проверить отказ для лишнего столбца, дубля ID, формулы и файла вне upload root.
7. Добавить пустой вариант, заполнить его цену/артикул/остаток и сверить ID.
8. Добавить видео и привязать тестовое изображение к цвету.
9. Найти run ID через change journals, получить undo preview и восстановить только изменённые поля.
10. Проверить set/add остатков, exact revisions и подтверждение обнуления.
11. Сверить найденные дубли названий, slug, штрихкодов и артикулов вручную.

## 9. Интеграции

- `addshop_integration_catalog` — сверить доступные контракты.
- `addshop_integration_status` — секреты должны отображаться только как configured.
- Секреты передавать через `env:ADDSHOP_SECRET_*`.
- Ozon/Wildberries/YML import обязан остаться preview-only.
- Для Яндекс Маркета проверять флаги цен, остатков и заказов по одному.
- Реальные импорты, посылки и платежи не тестировать на production-магазине.

## Критерии успешной приёмки

- пароль, cookies и API-ключи отсутствуют в ответах и журналах;
- каждое изменение имеет preview и verification read;
- stale revision блокирует запись;
- POST не повторяется автоматически после timeout;
- массовые операции начинаются только после snapshot;
- магазин остается в исходном состоянии после тестов.
